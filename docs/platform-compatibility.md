# macOS and Linux compatibility assessment

Assessed: 2026-10-01. The existing tested packaging target is Windows. This assessment defines the work for the macOS/Linux packaging milestones; it does not establish native runtime compatibility from Windows tests.

## Current evidence

The assessment began with NSIS and portable Windows artifacts only, with GitHub draft update metadata. Experimental `package:mac` and `package:linux` commands now configure DMG/ZIP and x64 AppImage/DEB, retaining `--publish never`. `verify:platform-config` checks the installed builder schema and stable identities/targets/security invariants. `scripts/generate-icons.mjs` now creates PNG/ICO, PNG-backed ICNS, Linux icon sizes and macOS template tray resources. Encoding/decoding and broken-configuration regressions pass on Windows.

`scripts/verify-release-artifacts.mjs` retains Windows validation. The new `scripts/verify-platform-artifacts.mjs` is wired into macOS/Linux packaging and validates required artifacts, container signatures, executable architecture, external macOS/embedded AppImage blockmaps, exact manifest checksums/sizes, packaged update configuration and required real ASAR entries. Native macOS validation runs `hdiutil verify` and ZIP integrity/content listing; native Linux validation inspects DEB architecture/content with `dpkg-deb`. It refuses to substitute a foreign host for those native tools.

The verifier's controlled regressions use real ASAR files, architecture headers, embedded/external blockmaps and intentionally broken metadata/resources. Their injected native checks let them run on Windows. Native hosted jobs now independently verify real Linux AppImage/DEB and Intel/Apple Silicon DMG/ZIP artifacts, then launch unpacked and extracted/mounted packages. Artifact consistency and runtime launches are separate checks; both pass in the hosted evidence below.

Commands: `npm run verify:platform-artifacts -- mac release arm64` on a matching macOS packaging host, or `npm run verify:platform-artifacts -- linux release x64` on Linux. macOS's default architecture is the host architecture; Linux packaging currently selects x64 explicitly. Manifest naming follows the installed builder: `latest-mac.yml`, `latest-linux.yml` for x64, and architecture-suffixed Linux manifests where applicable. Package commands run the verifier after builder success, with publication disabled.

The renderer, provider adapters, Node SQLite stores, managed files and loopback OAuth callbacks use mostly portable APIs. Main/preload builds are JavaScript and there are no application-owned native addons to rebuild. That reduces porting work, but Electron's embedded SQLite runtime, utility workers, package layout and sandbox still require native smoke tests.

`electron/main.ts` now registers login startup on Windows/Linux and verifies macOS registration, sets the Windows application ID conditionally, installs a macOS application menu, creates frameless windows and platform-specific tray images, and has a macOS-specific last-window lifecycle. `electron/update-policy.ts` explicitly refuses every non-Windows update. The assessment found a Windows-specific vault error and missing explicit rejection of Linux's weak storage fallback; the shared storage guard described below now fixes both. Native Linux and both macOS architecture jobs now pass; see the hosted evidence below.

## Packaging plan

| Concern | macOS | Linux |
| --- | --- | --- |
| Initial artifacts | Separate arm64/x64 DMG and ZIP; retain matching update metadata and blockmaps. | x64 AppImage and DEB; add arm64 only with matching native evidence. |
| Builder configuration | Stable bundle ID, category, icon, artifact names containing architecture, hardened runtime, conservative entitlements. Use installed v26 schema. | Stable executable/desktop identity, category, icon sizes, artifact names containing architecture and required runtime dependencies. |
| Native CI | macOS runner builds/packages and launches actual Electron and the extracted app bundle. | Ubuntu runner with Xvfb, D-Bus and Secret Service packages builds/packages and launches actual Electron and unpacked app. |
| Artifact verification | DMG/ZIP existence, ZIP content, architecture, app executable/resources, update manifest size/checksum and blockmaps. | AppImage/DEB existence, package metadata and executable/resources, architecture, manifest size/checksum and blockmaps where emitted. |
| Publication behavior | Local/CI packaging uses `--publish never`; no platform release implied. | Same; packaging does not publish or install artifacts. |

Use macOS hosts for macOS artifacts and Linux hosts for Linux packages. Keep Windows artifact names, verification and signing checks intact. Separate output directories or architecture-specific jobs prevent manifests overwriting one another. Package commands must run build/preflight/resource generation and verify the resulting platform artifacts, not merely accept electron-builder's exit code.

Electron-builder v26 documents DMG and ZIP as the macOS update pairing and supports signing/hardened-runtime configuration. The installed project's v26 types and schema are authoritative; current v27 signing examples use a different shape. [v26 macOS configuration](https://www.electron.build/v26/docs/mac/)

## Credential storage

Preserve OS-encrypted OAuth and IMAP vaults, atomic writes and restrictive file modes. Implemented: `electron/mail/secure-storage.ts` provides the platform-neutral guard used by `OAuthVault`. It refuses `basic_text`, unavailable storage and an unknown/unrecognized Linux backend before encrypted reads or writes; it leaves the last on-disk vault untouched. A local-only workspace remains usable when credential storage is unavailable.

Electron documents Keychain on macOS, DPAPI on Windows and desktop-dependent secret services on Linux. Its Linux `basic_text` fallback uses a hardcoded password and does not provide the protection Aerio promises. Consistent macOS signing also affects Keychain identity across updates. [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)

Implemented deterministic tests cover macOS/Windows availability and all recognized Linux backends, with vault regressions demonstrating refusal before read/write and preservation after a backend becomes unavailable. Native Linux CI should additionally test both a disposable unlocked Secret Service and an intentionally unavailable backend. Fixture-controlled cryptography is separate from proof that a real backend can encrypt/decrypt across process restart. Do not expose credential content in diagnostics.

## Native integration

The original assessment required native macOS application/editing/window menus, last-window Dock activation, full quit, message-window routing, restored bounds and a suitable template tray image. Implementation and the tested interaction boundaries are recorded below.

Implemented macOS policy: `electron/mac-integration.ts` supplies native application/editing/window menus and an explicit workspace reopen action. Main uses template tray images at 72/144 DPI, reads `wasOpenedAtLogin` for minimized startup, and verifies that a registration request produces an enabled native login item. Rejected/pending requests and status-query failures attempt to restore the prior registration and leave the preference unsaved; the renderer surfaces the original failure reason even if cleanup also fails. Regression fixtures verify removal of a newly pending item and preservation of the original native error. Electron warns that unsigned/unnotarized apps may fail registration silently. This does not claim signed-release startup readiness. [Electron login item APIs](https://www.electronjs.org/docs/latest/api/app)

`scripts/mac-integration-audit.mjs` checks real application menu roles, Cmd+A/C editing, accepted/rejected login registration and cleanup, lock-preserving tray/Dock activation, last-window closure/recreation, display-aware bounds persistence, menu reopening and native Cocoa Quit. The packaged audit also verifies actual Keychain encryption/decryption across restart, SQLite/worker IPC, local data and sandbox checks. `scripts/mac-container-audit.mjs` repeats it against a `ditto`-extracted ZIP and read-only mounted DMG, then ejects before cleanup. All three launches pass on both hosted macOS architectures. Dock activation tests emit the production event; Cocoa Quit uses [Electron's native responder API](https://www.electronjs.org/docs/latest/api/menu#menusendactiontofirstresponderaction-macos). Renderer-injected Cmd+Q did not trigger native quit on the runner, so physical Cmd+Q and Dock clicks remain unverified.

macOS login registration can use Electron's supported API for installed packages, with login-launch detection and minimized startup handled independently of Windows command-line flags. Linux requires an owned XDG autostart desktop entry or a visibly unsupported startup control; simply persisting a checkbox is insufficient. Resolve desktop entry paths safely, quote executable paths and remove only Aerio's owned entry when disabling. Test paths containing spaces and special characters. [Electron application and login APIs](https://www.electronjs.org/docs/latest/api/app)

Implemented Linux registration: `electron/linux-login.ts` writes an owned `aerio.desktop` under the absolute XDG config home (or `~/.config`), selects the persistent AppImage path when available, and adds `--aerio-login`. It uses an atomic replacement with restrictive file permissions, refuses unowned/linked entries and linked autostart directories, and removes only its owned entry. Packaged preference saves propagate registration failures before recording success. Disabled, unchanged preferences do not touch unrelated entries. The location follows the [XDG autostart specification](https://specifications.freedesktop.org/autostart/latest/).

`scripts/linux-login-exec-audit.mjs` uses the real `gio` desktop launcher to verify paths containing spaces, quotes, backticks, dollar signs, backslashes, percent signs and semicolons reach the executable unchanged with exactly the login argument. No shell is involved. A fixed `/usr/bin/env` executable avoids GLib validating a percent-escaped application path before expanding desktop field codes; GLib's implementation performs those operations separately. [Desktop Exec escaping](https://specifications.freedesktop.org/desktop-entry/latest/exec-variables.html), [GLib desktop launcher implementation](https://gnome.pages.gitlab.gnome.org/glib/coverage/gio/gdesktopappinfo.c.gcov.html)

Linux tray availability depends on the desktop. Never hide the sole window into an inaccessible tray: check creation/failure and keep a usable foreground/Dock/taskbar path. Test close-to-tray/full quit, notifications and routing, display changes, xdg-open/external links, print/file dialogs and shell-open errors. Notifications must respect app lock and global/account preferences on every platform.

Implemented: tray creation failures and empty icons preserve a usable window. Linux background close queries the StatusNotifier watcher's registered-host property through a bounded `gdbus` call; missing tools/services, false or malformed replies retain a minimized taskbar window. Close locks the workspace before either background path. While hidden, a three-second host check restores a minimized taskbar window if the host disappears. Activation also handles Linux's `click` event. Electron documents Linux activation as `click`, while `double-click` is a macOS/Windows event. [Electron Tray API](https://www.electronjs.org/docs/latest/api/tray)

Native unpacked, extracted AppImage and extracted DEB audits pass the no-host fallback in an isolated Openbox session: the real window remains alive, visible to the taskbar and minimized; app lock stays enabled and locked, and data survives restore/unlock and restart. Shared regressions cover registered/absent/malformed/failed host probes and an unusable tray. The full Linux desktop suite passes with the new close behavior. Legacy Gtk/XEmbed-only desktops conservatively retain the taskbar window because this probe does not verify their tray host.

`scripts/linux-tray-host-audit.mjs` and `scripts/fixtures/linux-tray-host.py` now provide the registered-host proof on an isolated D-Bus session. The actual Electron tray registers with the controlled watcher; calling its real StatusNotifierItem `Activate` method reopens the locked workspace. Closing again hides to the reachable host; terminating the host restores a minimized taskbar window within the monitor interval, preserving app lock. These checks pass for the unpacked app and both extracted containers. The fixture uses the KDE watcher interface and verifies protocol behavior, not a particular desktop's tray rendering. [KDE watcher interface](https://github.com/KDE/plasma-workspace/blob/master/xembed-sni-proxy/org.kde.StatusNotifierWatcher.xml)

The full Windows desktop sequence also passes after the fallback change, including context menus, accessibility, recovery/backup, app lock/preferences and all Google/Microsoft task audits. Both hosts pass type checking and the shared unit suite. The native audit seeds local data before renderer hydration to avoid an out-of-band test write racing the renderer's original autosave.

Preserve context isolation, sandboxed renderers, navigation denial, main-owned attachments and loopback OAuth state/PKCE. Linux test infrastructure may require a display and D-Bus; do not disable production Chromium sandboxing or force plaintext credentials to make CI green.

## Updates

Retain the current Windows update policy initially. New unsigned CI builds must explain that automatic updates are unavailable and direct users to the release source; no startup update timer should run on those builds. That is an explicit platform limitation, not a claim that packaging automatically enables self-updating.

For a future signed macOS updater, DMG/ZIP metadata and matching application signatures must be proven before enabling it. Linux AppImage updating depends on the installed format/environment; DEB ownership and system package-manager behavior need a separate policy. Do not turn on a Linux updater merely because the app is packaged. The assessment recommends format-aware gating and separate test fixtures before activation. [v26 update requirements](https://www.electron.build/v26/docs/features/auto-update/)

Platform artifact checks should validate emitted metadata even while runtime updates remain disabled. Metadata correctness does not establish signature trust, hosted discovery or successful installation. These checks can be automated without adding account/signing/publishing actions to the Codex roadmap.

## Implementation and proof boundaries

The packaging milestones now include platform commands/configuration, native CI, artifact checks and platform-specific automated coverage. Hosted validation exposed and fixed a backup-restore autosave race, platform assumptions in lifecycle/selection tests and asynchronous test races. Shared unit/type/build checks, real Electron lifecycle/storage fixtures and packaged-container launches pass on each native CI host.

Native evidence so far: `npm run package:linux` builds x64 AppImage/DEB in Ubuntu under WSL2 and both pass the real native artifact verifier. This exposed and fixed target-specific architecture labels (`x86_64` for AppImage, `amd64` for DEB). `desktopName: aerio.desktop` and `linux.syncDesktopName` establish consistent Linux window/desktop identity.

`npm run test:platform:linux` runs the unpacked packaged executable as an ordinary user in a disposable HOME, Secret Service session and virtual display. It passes sandbox/context isolation, main/preload/SQLite/worker IPC, preferences and local data across full process restart, actual `gnome_libsecret` encryption/decryption across restart, app lock and disabled updater checks. It also enables startup through production preference IPC, verifies the owned entry, relaunches with the login argument and checks actual minimization, then disables startup and verifies removal. This tests registration and launch behavior; it does not simulate a complete desktop login. It uses synthetic data and no mail credentials. The credential check proves the OS backend round trip; vault refusal behavior is covered separately by unit tests. `test:platform:mac` runs the shared packaged audit plus macOS integration checks and passes on both hosted architectures.

`npm run test:platform:linux:containers` extracts the built AppImage with its own runtime and extracts the DEB with `dpkg-deb`; both resulting packaged executables pass the native audit. This proves extracted-container launches, not FUSE mounting or a system DEB installation. The container audit also checks the DEB desktop entry identity. Disposable profiles, keyrings and extracted files are removed afterward.

`npm run test:platform:linux:desktop` passes the full source Electron sequence under Xvfb, Openbox and a disposable Secret Service: buttons, context menus, accessibility, recovery, backup, app lock, preference persistence, and all four Google/Microsoft task audits. These checks use controlled providers. The window manager makes maximize/restore meaningful; mail pane separators are tested in the connected-account fixture rather than transient empty-account onboarding. The shared unit suite passes 1,001 tests on Linux and macOS and 1,000 on Windows, where the Linux symlink fixture is skipped.

`.github/workflows/linux.yml` installs the native test dependencies, runs unit/IMAP/matrix and desktop checks, packages without publication, runs unpacked/extracted-container audits, and retains Linux artifacts. The complete [hosted Linux workflow](https://github.com/themuddfamily/aerio/actions/runs/37122361234) passes on 2026-10-03 and retains `aerio-linux-x64` artifacts. The disposable Ubuntu runner permits unprivileged user namespaces so Chromium can use its sandbox; the app still requires sandboxed renderers and never adds `--no-sandbox`. Ubuntu documents this host restriction and its sysctl control. [Ubuntu user-namespace policy](https://ubuntu.com/blog/ubuntu-23-10-restricted-unprivileged-user-namespaces)

Linux `test:imap` also passes TLS/STARTTLS, worker restart/recovery and the read-only loopback live-runner check. The disposable WSL source copy excludes the project's Git history; an empty fixture repository supplies the runner's required provenance fields for this synthetic test. `test:live-matrix` passes structural validation and explicitly reports hosted results as unverified.

The 2026-10-01 dependency refresh was verified with the CI runtime, Node 24.21.0, on the disposable Linux source copy. Clean `npm ci` and `npm audit` reported zero known vulnerabilities. All 999 unit tests, TLS/STARTTLS integration, the full desktop suite, packaging/artifact verification and native unpacked/extracted AppImage/DEB audits passed with Electron 43.7.7 and Nodemailer 10.0.13. This was local native evidence; the 2026-10-03 hosted runs below add native CI proof and the backup-restore regressions.

Hosted evidence: [Linux x64](https://github.com/themuddfamily/aerio/actions/runs/37122361234) and [macOS Intel/Apple Silicon](https://github.com/themuddfamily/aerio/actions/runs/37122361273) pass for validation commit `634972ff46930c56c535d38615848d7d815ddab7` on branch `codex/native-validation-20261003-112950`, on 2026-10-03. The jobs retain `aerio-linux-x64`, `aerio-macos-x64` and `aerio-macos-arm64` artifacts. The matrix uses controlled providers; real hosted-provider compatibility remains unverified. A virtual-display suite and controlled tray host do not establish every physical desktop's tray or notification service.

`.github/workflows/macos.yml` runs independent Apple Silicon (`macos-15`) and Intel (`macos-15-intel`) jobs with Node 24, shared unit/IMAP/desktop checks, native packaging verification and unpacked/ZIP/DMG audits. Both jobs pass and retain their architecture-specific artifacts; packaging never publishes a release. Runner labels follow [GitHub's runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Current shared unit results are 1,001 passes on Linux/macOS and 1,000 on Windows (one Linux symlink fixture skipped).

Windows-hosted parameterized tests prove policy and manifest handling. The hosted native jobs now additionally establish Keychain/Secret Service round trips, native container verification and tested packaged launches. They do not establish signing/notarization trust, physical Cmd+Q/Dock interactions, FUSE mounting, system DEB installation, a complete desktop login, notification delivery on every desktop or real hosted-provider compatibility. This assessment and the automated packaging/runtime milestones are complete within those evidence boundaries.
