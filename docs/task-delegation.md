# Task delegation by email

Open Tasks → Delegated tasks to send a request or review assignments. A **Delegate** button beside local and connected tasks copies the title, notes and date-only due date and keeps an **Open original task** link. The original task remains independent: acceptance or completion of the delegated copy does not silently edit a Google, Microsoft, DAV or local source task.

Choose a connected sending account, recipient and task, then click **Send task request**. This explicitly queues an RFC 5546 VTODO REQUEST as RFC 6047 iMIP mail. The recipient needs a client supporting VTODO scheduling; many calendar invitation clients support VEVENT meetings only. Aerio recognizes supported requests when raw messages arrive during mail sync or when a calendar attachment is opened in Mail. Previously cached messages can be recognized by opening them. Requests addressed to an account's primary address or a known sending identity appear in Delegated tasks.

Recipients can **Accept and send reply**, **Decline and send reply**, and, after acceptance, **Send progress** or **Complete and send reply**. Each action explicitly queues a real VTODO REPLY to the organizer. A reply comment is optional. Organizers can edit the request and **Send updated request**, which increments its sequence and asks the recipient to accept the revision, or confirm **Cancel assignment** to send a CANCEL. The task view shows the response, percentage and each message's actual Outbox/Sent/failure state. A locally selected response can be waiting for delivery: it is not proof that the other person has received it.

## Provider boundaries

- Google Tasks [`assignmentInfo` is output-only](https://developers.google.com/tasks/reference/rest/v1/tasks). Assignments created in Docs/Chat stay read-only through Aerio's existing Tasks connector. Delegation mail creates a separate task request; it does not create a native Google assignment.
- [Microsoft Graph To Do's task API](https://learn.microsoft.com/en-us/graph/api/resources/todotask?view=graph-rest-1.0) has no assignee/assignment write API. This feature does not claim native To Do assignment or Planner support.
- CalDAV ORGANIZER/ATTENDEE properties alone do not establish a task delivery capability. For example, [sabre/dav scheduling supports VEVENT only](https://sabre.io/dav/scheduling/). Aerio uses explicit mail transport instead of pretending that writing those fields sent a request.
- Outgoing requests include required DTSTART and PRIORITY properties; the date-only start defaults to today, or the day before a due date that is today or earlier. Progress/completed replies use the VTODO IN-PROCESS/COMPLETED participation values. Supported scheduling messages are a single non-recurring VTODO with one organizer, one assignee and a date-only DUE. Recurring requests, multiple assignees, time-valued due dates, COUNTER and reassignment chains are not imported as supported assignments. Full compatibility with proprietary Outlook/EWS task-request formats is not claimed. The protocol is [RFC 5546 §3.4](https://www.rfc-editor.org/rfc/rfc5546#section-3.4), carried by [RFC 6047](https://www.rfc-editor.org/rfc/rfc6047).

## Durability and correlation

Ledger changes, calendar payloads and the existing durable draft queue entry commit together in Aerio's mail SQLite database. Gmail, Microsoft Graph, Exchange EWS and IMAP/SMTP use their existing send paths. Offline operations and calendar MIME survive restart. Requests are visible in Outbox; task-message editing uses the task request editor so the mail envelope and calendar data cannot diverge. Native delivery failures remain failed until explicitly retried. Before retrying an uncertain delivery, inspect Sent mail: a transport can lose the response after the server accepted a message.

Incoming requests are scoped to account and UID and must name one of that account's addresses as assignee. The mail From address must match the organizer; replies must match the stored assignee and organizer, UID and exact request sequence. Duplicate and older requests/replies do not replace newer state. Replies use monotonic DTSTAMP values, and cancellation tombstones stop an out-of-order earlier request resurrecting a cancelled task. Sender-address correlation is not cryptographic sender authentication; normal mail trust and authentication still apply. Incoming messages never send a response automatically. Removing a source task does not cancel its independent assignment; use the assignment's cancellation action.

## Validation

`npx vitest run electron/mail/task-delegations.test.ts electron/mail/task-delegations-transport.test.ts src/components/TaskDelegation.test.tsx electron/mail-worker.test.ts` covers the full request/accept/decline/progress/complete/update/cancel lifecycle, malformed/stale/duplicate messages, sender/account isolation, offline restart, atomic rollback and the normal provider queue. The SMTP integration test sends actual calendar MIME only to a disposable authenticated TLS server with a trusted test certificate; it verifies recipient-side recognition and response delivery without real accounts.

After `npm run build`, run `npx tsx scripts/desktop-task-delegation-audit.mjs` for a real Electron UI audit with synthetic disconnected mail accounts: create an offline request, restart, recognize the recipient copy and explicitly queue acceptance. No real provider credentials or destinations are used.
