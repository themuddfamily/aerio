# Task provider integration

Google Tasks and Microsoft To Do share the contract in `src/task-provider-types.ts`. A provider snapshot contains task lists, flat task records with stable parent identities, provider revisions, and per-list incremental checkpoints. The local Tasks view's embedded checklist, priority, and recurrence are separate presentation/local-state concerns. Both adapters, durable task/list stores, mutation engine, service, OAuth consent detection, IPC/preload API, and provider Tasks interfaces are implemented and tested. Existing local task lists remain separate from provider lists.

## Google adapter

`electron/productivity/google-tasks-connector.ts` implements paginated list/task reads, incremental refresh, task/list CRUD, subtask creation, and reparenting. Identifiers include encoded account, list, and task IDs, avoiding cross-account/list collisions. The snapshot retains parent links and positions rather than collapsing remote subtasks into an unversioned local checklist.

The [Google task resource](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks) exposes ETags, parent IDs, completion, notes, and due dates. Due dates contain calendar dates only: Google discards the time portion. The documented schema does not expose recurrence or priority, so the adapter advertises those as local capabilities. Assigned tasks are imported read-only because deleting an assignment through the API can also delete its source in Docs or Chat. Missing revisions and missing write consent also prevent writes.

[Incremental reads](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks/list) use `updatedMin` with completed, hidden, deleted, and assigned records included. Checkpoints derive from provider modification timestamps, with one second of overlap; an empty delta does not advance a desktop-clock watermark. Refresh preserves unchanged records, applies tombstones, removes disappeared lists, and returns a replacement snapshot only after every page succeeds. Invalid incremental filters trigger a full read for the affected list. A repeated page token fails the refresh rather than looping.

Updates and deletions require the original cached ETag. The adapter compares it to the current resource before sending a write and also sends `If-Match`, following Google's [read-modify-write guidance](https://developers.google.com/workspace/tasks/performance). A changed revision or server-side 412 remains a conflict; the adapter does not fetch a newer revision and overwrite the other client's changes. Write calls are not automatically retried, since a lost creation response can otherwise create duplicate tasks. The durable operation layer must resolve uncertain results explicitly.

## Durable state and operations

`electron/productivity/task-store.ts` stores provider snapshots, stable local UUIDs, local priority/recurrence/timed-due metadata, original mutation revisions, and operation history in SQLite. A provider-assigned identity attaches to the existing local UUID. Snapshot replacement is atomic and preserves local metadata and queued projections; refreshing never changes an operation's original revision. Successful writes rebase their queued successors onto the revision returned by that write. Startup holds interrupted writes under review because a lost response cannot establish whether the provider accepted them.

`electron/productivity/task-sync-engine.ts` processes writes one at a time, coalesces concurrent flush calls, respects offline state and disconnected accounts, and waits for parent creation before creating a child. Conflicts block later edits to the same task while unrelated work proceeds. Definite rate-limit responses receive bounded backoff; ambiguous network/server failures require review and are never automatically resent. Failure categories stored for display exclude raw provider errors.

Undo cancels unsent changes or queues a revision-protected compensating write after success. Undoing an unsent parent creation also cancels its dependent child creations and edits. Restoring a deleted task preserves its local identity and obtains a fresh remote identity. Undo restores the actual pre-write baseline, so cancelled optimistic changes cannot reappear. Deleting a parent with subtasks currently requires deleting or moving those subtasks first; automatic subtree deletion is not implemented. A compensating create has the same uncertain-result safeguards as ordinary creation.

Recurring completion records its operation, a successor creation, and the source-to-successor occurrence identity in one transaction. A source task owns one successor; reopening and completing that same source again cannot duplicate it. The successor becomes visible offline immediately but cannot send until the completion succeeds. Conflicted or uncertain completion therefore cannot publish a new occurrence. Subtasks are copied with fresh local identities and reset completion, with remote writes waiting for their new parent. Priority and recurrence metadata carry forward.

`task-recurrence.ts` advances daily/weekly/monthly dates in UTC, clamping monthly dates to the last valid day (including leap years). Google due values remain calendar dates; timed due details stay local. An undated occurrence uses completion time as its initial date. This is deterministic UTC arithmetic; preserving a named local timezone across daylight-saving changes is not implemented. Recurrence is triggered by completion in Aerio, rather than by observing another client's completion during refresh.

Undoing an unsent completion cancels its generated successor and children atomically. If a successor write is running, uncertain, or already accepted, undo requires resolving or undoing that successor first. Once its compensating deletion is confirmed, the source completion can be undone. Cancelling an unsent parent also cancels moves into that parent while preserving unrelated edits to existing tasks.

Explicit resolution supports discarding an operation and its pending successors, retrying against a reviewed current revision, or accepting a matching refreshed result. Retrying uncertain writes additionally requires explicit confirmation that they were not applied. Accepting a creation can merge a pristine imported provider record into the original stable local identity, preserving local metadata and repairing child references; candidates with their own local changes are rejected. A durable resolution history retains the previous operation status and revision. Accepting completion requires its completion state to match; accepting deletion requires absence from a full refresh. Unchanged baseline revisions are never silently replaced during ordinary refresh.

## Desktop service and consent

The main process initializes `provider-tasks.sqlite` independently of existing local productivity data. `task-service.ts` serializes refresh, mutation dispatch, and explicit reconciliation. Local edits are persisted before network processing; the automatic queue reloads account settings before dispatch. Startup and minute polling refresh eligible Google accounts incrementally and flush pending work. Network reconnection also flushes. Account failures remain independent of other task accounts and Calendar/Contacts synchronization.

When a restored write grant meets caches imported under read-only consent, dispatch first refreshes those permissions without changing queued original revisions. A failed permission refresh holds that account's queue, preserving unattempted writes, while other accounts continue. Renewed consent never makes uncertain or restored writes eligible for automatic replay.

Google authorization now requests the [documented Tasks scope](https://developers.google.com/workspace/tasks/auth). Stored token scopes determine access: `tasks.readonly` permits reads, and `tasks` permits writes. Legacy grants do not imply Tasks consent. The existing reconnect flow can obtain new consent; Aerio never starts an authorization dialog automatically. The typed `window.aerio.tasks` API exposes snapshots, refresh, create/update/delete/move, local metadata, undo, explicit resolution, and change events. Reconciliation performs a full provider refresh before any acceptance or retry and checks the revision the user reviewed.

Archiving or disabling synchronization stops task dispatch; archived task caches and pending intent remain visible and read-only. Deleting an account removes its provider task entities, snapshots, queue, recurrence links, and resolution history atomically after in-flight work settles. Archive/delete transitions immediately publish refreshed account visibility. Reconnect or reenabling synchronization resumes the service. Paused synchronization is labeled separately from missing consent. Shutdown stops polling and closes the store after queued service work settles; interrupted remote writes still enter review on the next launch.

`task-store.test.ts` exercises real SQLite transactions, failure rollback, restart, identities, hierarchy validation, baselines, undo, recurring completion, successor identity, copied-subtask cancellation, explicit resolution, and atomic editor metadata/field saves. `task-sync-engine.test.ts` covers ordered dispatch, overlapping flushes, permission changes, conflicts, rate limits, uncertain results, parent and completion dependencies, compensation, and persistence failures with controlled connectors. `task-service.test.ts` covers offline edits, consent, independent accounts, full reconciliation refresh, serialization, archival, deletion, and restart queue processing. OAuth/main-process fixtures cover consent scope checks and IPC routing; the Electron recovery audit verifies existing desktop lifecycle behavior with the initialized task service.

## Tasks view

`TasksView.tsx` loads the typed task snapshot and subscribes to change events. Google lists appear under their accounts in the sidebar, alongside existing local lists. Selecting a provider list opens `ProviderTasksPanel.tsx` with search, completion filters, date-only due values, parent links, local priority/recurrence controls, read-only enforcement, refresh, create/edit/delete, reparenting, recent changes, and undo. Creating or updating task fields and local settings is one durable transaction. Changing a parent uses an explicit move action, separate from editing fields.

Conflict and uncertain-result review shows readable local changes and the latest provider version. Users can refresh, discard local intent, retry against the reviewed revision, or match an uncertain creation to a selected provider record. Uncertain retries require a not-applied confirmation. All unresolved operations remain visible beyond the recent-history limit. Save failures keep editor input and display an error within the dialog. Read-only or assigned tasks remain viewable while write controls are disabled; legacy accounts offer the existing consent/reconnect flow.

Matching an accepted result treats absent notes and an empty string as equivalent. Nonempty text, including whitespace, must match exactly. This allows “Confirm applied” to recognize Google's empty-string response to a note clear without reissuing an already accepted write. Store regressions cover both empty representations, omitted empty notes on creation, and mismatching nonempty results.

## Provider list management

Each Google account in the Tasks sidebar has **Manage lists**. Its dialog creates lists, renames existing lists, confirms deletion of a list and all its tasks, and reviews pending list changes. List creation is durable offline; the list appears when Google confirms its native identity. Until a write is sent, it can be cancelled. Existing local task lists use their separate controls.

`task-list-queue.ts` shares the task SQLite database and transaction boundary. Creation, rename, and deletion intent includes original list revisions and durable status/attempts. Ordinary refresh never rebases a queued list revision. Only one unresolved rename/deletion can target a list at a time. Deletion rejects pending task changes and read-only/assigned tasks; once queued, it prevents new task edits. Confirmed deletion removes that list's snapshot/checkpoint and task visibility atomically, preserving historical rows. List deletion cannot be undone; the dialog states that before confirmation.

Interrupted or ambiguous list writes enter review and never automatically replay. Review refreshes all provider lists before accepting absence, matching a newly created list, or retrying a reviewed revision. Uncertain retries require confirmation that the write was not applied. A lost creation cannot attach to a list already known before creation or claimed by another creation. Resolution history preserves the old revision/status. Bounded 429 backoff and sanitized rejection/conflict categories follow task dispatch behavior. Account deletion purges the list queue as part of the same transaction.

Connected-task backups include validated list operations and their resolution history; existing backups without that optional section remain supported. All restored active list writes are held under `restored-write` review, including originally unsent creations. Real SQLite fixtures cover offline persistence, restart, old revisions, conflict retry, accepted-result persistence rollback, duplicate matching, protected deletion, malformed backup rejection, restore rollback, and account removal. The native write audit covers list CRUD, conflict review, and create/delete lost responses without duplicate writes. The offline audit covers native backup/restore/restart of list intent and its review UI.

## Connected task backups

The Tasks sidebar provides **Back up connected tasks** and **Restore connected tasks**. This versioned JSON format (`aerio-provider-tasks`, schema 1) is separate from Settings' existing local Tasks/Notes/Contacts backup. It includes cached provider lists/tasks, stable local identities, priority/recurrence/timed-due metadata, initial fields, durable operations and baselines, occurrence dependencies, and resolution history. It excludes OAuth tokens, credentials, attachments, and filesystem paths. File import/export is capped at 150 MB.

`task-backup.ts` validates supported schemas, bounded records, allowed fields, timestamps, account/list ownership, unique identities, acyclic hierarchy, operation ordering, dependency/undo references, occurrence ownership, and resolution references. A detached validated graph is restored in one SQLite transaction, rolling back the replacement on any insertion failure. Export reads all records in one transaction. Both operations share the service's serial lane so accepted provider results cannot race restoration.

Restore explicitly replaces connected-task caches and history after the user confirms; local Tasks/Notes/Contacts remain unchanged. Every active operation—queued, running, failed, conflicted, or under review—becomes `review` with `restored-write`. Original attempts, revisions, intent, and history remain available, but retry timestamps are cleared and no restored write is automatically eligible. Provider checkpoints are cleared so subsequent refresh is complete. Successful/cancelled history stays historical; undo remains an explicit action subject to revision protection. Discarding an unsent restored creation or recurring completion also cancels its never-attempted descendants, avoiding orphan review state.

Restored accounts absent from current mail connections appear as **Recovered Google tasks**, read-only. Their caches can be viewed and exported before reconnecting the matching account. Reconnecting never bypasses restored review holds. `task-backup.test.ts` exercises complete round trips, offsets/Unicode, original identities/revisions, recurrence/history, no replay after restart, malformed reference graphs, credentials rejection, and SQLite-failure rollback. Main/service/UI fixtures cover file validation and size limits, confirmation, recovered accounts, and preserved local state. The native task audit verifies the actual export/import file path and review UI across restart.

## Microsoft To Do integration

`microsoft-tasks-connector.ts` implements the shared connector contract and is wired into the desktop service and interface. It paginates lists and task delta rounds, hydrates partial task deltas, and rereads surviving parents' paginated checklist items because checklist changes can occur independently of parent changes. Expired checkpoints rebuild the list from a full delta round. Continuation and checkpoint URLs must stay on the exact Graph origin and collection path before receiving authorization; loops and incomplete rounds fail without replacing the cached snapshot.

Native task records preserve recurrence patterns/ranges, importance, progress state, due wall-clock values and their provider time zones, and the original text/HTML body. Display notes are plain text. Unrelated edits omit body, recurrence and due fields to preserve provider data; edited notes are escaped into HTML. Explicit-offset due inputs normalize to UTC, while inputs without offsets retain the requested or existing native zone. Checklist items have separate parent-scoped identities and support title/completion only. Nested checklists and reparenting are rejected rather than simulated.

Tasks without native ETags remain read-only. Lists and checklist items use native ETags when supplied; otherwise they keep a deterministic snapshot fingerprint and compare the original snapshot against a GET immediately before writing. Snapshot hashes are never sent as HTTP ETags. A snapshot comparison cannot prevent another edit between GET and write. The adapter sends `If-Match` for actual ETags, but the controlled tests do not establish hosted Graph conditional-write behavior. Managed/system lists are protected, and ambiguous writes are never automatically retried by the connector.

`microsoft-tasks-connector.test.ts` currently contains 25 controlled adapter/validation checks covering pagination, partial/empty/expired deltas, independent checklist changes, deletions, account isolation, continuation security, failed refreshes, field preservation/clears, task/list/checklist CRUD, original-revision conflicts, missing ETags, read-only access, unsupported operations, native recurrence defaults and lost write responses. No real Microsoft account is used.

The shared durable queue now preserves native fields in cached projections, original operation baselines, successful results, undo compensation and resolution history. Native patches merge individual fields, including explicit null recurrence clears. Plain-note edits supersede cached rich bodies; undo restores the original HTML and progress state. Local recurrence/priority/timed-due metadata is rejected for Microsoft, so native recurrence never generates a duplicate local successor. Checklist nesting/unsupported fields and reparenting are rejected before queue insertion; managed-list permissions are checked at insertion, retry and dispatch.

Connected-task backups validate the native field allowlist, recurrence shapes/defaults, revision modes, checklist parent ownership, and Microsoft Graph delta URLs scoped to the owning list. Large cached rich notes survive title edits and backup without truncation. Restore retains native intent but clears checkpoints and holds pending task/list writes for review. Accepted-result reconciliation checks only intended native fields, compares normalized due values with their expected time zones, and retains local identities without replaying ambiguous writes. `microsoft-task-state.test.ts` covers these paths with real SQLite persistence and the production adapter against controlled HTTP responses, including restart, undo of deletion, conflicts, independent native fields, and malformed restore rejection.

`OAuthVault` requests `Tasks.ReadWrite` during interactive Microsoft sign-in/reconnect and detects exact stored `Tasks.Read`/`Tasks.ReadWrite` grants without inferring Tasks access from mail permissions. Token refresh uses the existing stored scope; legacy credentials without recorded scopes use the pre-Tasks scope set. Adding this integration therefore does not request new consent through background mailbox refresh. Returned scopes remain authoritative, including read-only or missing Tasks grants. This follows Microsoft's [task delta permission contract](https://learn.microsoft.com/en-us/graph/api/todotask-delta?view=graph-rest-1.0) and [OAuth authorization/refresh flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow).

`TaskService` routes each account by its actual provider, exposes recovered Microsoft caches read-only, refreshes stale permission flags before dispatch, and holds queues across absent/read-only Tasks access, disabled sync, authentication failures and archival. A recorded Tasks write grant still permits saving cached offline intent during a mail authentication failure; network dispatch stays held until the account recovers. Deletion purges local data without provider writes. A Microsoft refresh failure does not block another Google account's writes. Account scopes are checked before task/history mutations. `microsoft-task-service.test.ts` covers these behaviors with the production shared service and SQLite store. The Google offline desktop audit also guards the separation between saving intent and dispatch eligibility.

The Tasks sidebar provides **Connect Microsoft To Do** and **Manage lists**. `MicrosoftTaskEditor.tsx` exposes native progress, priority, due wall-clock/time zone, all six recurrence patterns and three range types, and checklist creation under eligible parent tasks. Existing checklist items expose name/completion only; no reparent control is offered. Managed lists disable rename/delete while eligible tasks remain editable. Microsoft saves send only changed fields, preserving long cached notes, rich HTML and exact due timestamps during unrelated edits. Review dialogs use Microsoft labels and readable native intent/provider values. Interface regressions cover field-only saves, native priority/progress, explicit clears, annual weekday recurrence, checklist restrictions, list permissions and reconnect/review controls.
